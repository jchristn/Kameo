# Architecture and integration contracts

## Components

| Project | Responsibility |
| --- | --- |
| `Kameo.Core` | Profile domain, structured SQLite storage, private files, native imports, launch planning, process supervision, startup registration |
| `Kameo.Cli` | Thin command composition and terminal process lifetime |
| `Kameo.Desktop` | Avalonia manager, tray, palettes, dialogs, native menus, terminal launching |
| `Test.Shared` | Runner-independent Touchstone contracts, filesystem and process integration tests |
| `Test.Automated`, `Test.Xunit3`, `Test.Nunit`, `Test.Aot` | Shared test runners |
| `Test.Desktop` | Touchstone UI workflows and native lifecycle smoke testing |
| `Test.Harness` | Disposable synthetic child executable for argument, environment, exit-code and cancellation tests |

There is no HTTP server, remote account service, database server, or web dashboard. The only outbound requests Kameo makes itself are Claude usage checks, run on demand and every 15 minutes while the desktop is open, and the Claude sign-in renewal they trigger for idle profiles (see Plan usage). The backend reference's HTTP, multitenancy, Docker, REST/MCP, Postman, and four database-provider requirements do not apply to this local filesystem application. Unsigned installers for Windows, macOS, and Linux (x64 and ARM64) are built by `Kameo.Publisher` from `publisher.json` and published on GitHub Releases; see `INSTALL.md` and `RELEASING.md`. Installed layouts put `kameo` beside the desktop executable (Program Files, `Kameo.app/Contents/MacOS`, `/opt/kameo`), and the desktop looks there first. Users can also build the CLI as a local `Kameo.Cli` .NET tool package and install the `kameo` command for their user; this does not install or update the desktop. Source version is `0.2.3`, with alpha status in documentation and the UI.

## Storage and concurrency

`kameo.db` contains typed columns for profile identity, harness, authentication kind, API key, executable override, shared Mux endpoints-file path, creation time, selected profile per harness, and non-secret preferences. Schema version 2 adds `mux_endpoints_file` transactionally with an empty default, preserving existing rows and selections. Foreign keys prevent selecting a profile belonging to another harness. Case-insensitive unique names are scoped to each harness. PrettyId supplies stable prefixed K-sortable IDs.

Connections are short-lived and independent; operations use SQL parameters and transactions. Reads return detached snapshots and redact keys by default. Native profile directories are stable across invocations. Ordinary launches hold shared cross-process profile leases, allowing multiple sessions with the same profile and login. Edits, imports, deletion, and sign-in/setup require an exclusive lease, except Claude Code native sign-in, which joins open sessions with a shared lease (see Claude Code below). Selection is independent of those leases. A separate short-lived preparation lease serializes launch configuration and Claude Keychain synchronization, but is released before waiting for a harness to exit. Lease files are retained so all processes coordinate on the same files.

Files written by Kameo use bounded reads, link/reparse-point rejection, sibling temporary files, flush and atomic replacement. The store requires a private local filesystem with SQLite and file-lock support. Unix permissions are owner-only. Credentials are not encrypted by Kameo. Imported files are copied, never moved or modified. Only the authentication artifact is imported; harness hooks, plugins, histories, and settings are not copied from a user's default installation.

Vendor-native JSON is intentionally unmanaged third-party payload data. Kameo validates a minimum authentication shape and retains additional fields. It does not use opaque JSON blobs for its own structured profile metadata. The harness can create further state within its own profile directory.

Deletion removes local profile data and selection. It does not revoke a provider token or sign out the original imported account. A failed filesystem deletion may require cleanup before retrying; SQLite rolls back the metadata deletion. Deleting native Claude profiles on macOS also deletes their directory-scoped Keychain entry.

## Harness contracts

### Claude Code

Both `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` are pinned to the selected profile directory. The latter can override credential storage independently, including selecting the default Keychain entry when inherited as an empty string. `ANTHROPIC_CONFIG_DIR` points to an `anthropic` subdirectory of the profile so an expired subscription cannot fall back to an unrelated `ant` login. Inherited Anthropic profile, federation, identity-token, and federation-cache selectors are removed from child environments. These contracts were checked against installed Claude Code 2.1.331 and its [authentication precedence documentation](https://code.claude.com/docs/en/authentication#authentication-precedence).

**Sign-in alongside sessions.** A Claude Code native sign-in only replaces the profile's saved login, so it runs while sessions for that profile are open; running sessions read the saved login again when theirs stops working. This lets a profile whose sessions were signed out (Claude clears the login's tokens when a renewal is rejected) sign in again without closing them. The sign-in holds a shared profile lease, so edits, imports, deletion, and Kameo's own renewal still wait for it, and a sign-in lease (`locks/<id>.signin.lock`) for its whole duration. Launches check that lease under the preparation lease and refuse to start while a sign-in runs, so a launch cannot restore an older saved login over the one being written; a second sign-in for the same profile is refused. Other harnesses keep exclusive sign-in. Around `kameo login`, the CLI reads the account (the login's `accountUuid`, which Claude keeps even after clearing tokens, and `oauthAccount.emailAddress` from the profile's `.claude.json`) before and after, and prints a warning in the sign-in terminal when it changed. Whether a running Claude Code session picks up the new login without a restart depends on Claude Code and was not verified.

Explicit native sign-in adds `--email <profile-name>` when the name is an email address, unless the caller already supplies `--email`. This is a browser hint only; the user must confirm the intended browser account. Ordinary launches receive no login flags. Kameo does not manage browser cookies or bind a display name to a verified account identity.

Use `CLAUDE_CONFIG_DIR` and `ANTHROPIC_API_KEY` for API profiles. Native login invokes `claude auth login`. Linux/Windows native credentials live in `.credentials.json`. On macOS, Claude 2.1.331 always keeps its login in a Keychain service named from a hash of the config directory and has no setting to use the file instead, so Kameo keeps the two in step. The Keychain item is authoritative while it holds a usable login (non-empty access and refresh tokens): at every launch and after every exit, Kameo saves it to `.credentials.json` when it is at least as fresh (by `expiresAt`) as the file. Kameo writes the file back to the Keychain only at launch, and only when the item is missing, cleared (Claude blanks the tokens after a failed refresh), or older than the file. An unreadable Keychain stops the launch rather than risk replacing a newer login. Importing a Claude credential file deletes the profile's scoped item so the import wins at the next launch. Because refresh tokens rotate, restoring an older copy over a refreshed login would sign the profile out; this ordering prevents that even when a session ended without saving. Sessions can run for days, so every Claude usage check (including the desktop's 15-minute background check) also maintains the copy under the preparation lease, whether or not sessions are open: it saves a Keychain login at least as fresh as the file, and writes the file back over a cleared or older Keychain item once per saved version (`expiresAt`) per process, so a login Anthropic rejected is not restored repeatedly. A missing item is left for the next launch, and a running sign-in or unreadable Keychain skips the profile. Outside macOS the file is Claude's only store and there is nothing to maintain. The CLI handles SIGHUP and SIGTERM (a closed terminal window) by stopping the harness and synchronizing before it exits. Secrets are passed to the Keychain command through standard input in hexadecimal, never argv. Items are read with the user's account name (`$USER`) first, the name Kameo writes and Claude Code reads, and only then by service alone, because Claude can leave a stale item for the same service under another name such as `unknown`; deletion removes every item with the profile's service.

The service naming contract is `Claude Code-credentials-` plus the first eight lowercase hexadecimal characters of SHA-256 over the normalized explicit config directory. The default login service is `Claude Code-credentials`. This was checked against the published Claude Code package and the installed CLI's login help. [Claude credential management](https://code.claude.com/docs/en/authentication) documents the directory-scoped behavior; [environment variables](https://code.claude.com/docs/en/env-vars) documents configuration and API-key inputs.

### Codex

Set `CODEX_HOME` and pass `-c cli_auth_credentials_store="file"`. API profiles write their key into the profile's `auth.json`; native profiles retain the CLI's renewable login document. Browser login invokes `codex login`, with optional `--device-auth` forwarded by the CLI. No third-party OAuth implementation is involved. [Official authentication documentation](https://developers.openai.com/codex/auth/) describes the file store and native refresh behavior.

### Antigravity

`kameo antigravity` invokes `agy` with `--gemini_dir` pointing to a stable profile directory. API profiles supply `GEMINI_API_KEY` through the child environment and enforce `--settings {"modelProvider":"gemini"}`. Account profiles remove inherited provider credentials, remove the persisted `modelProvider`, and override it with an empty value for the native provider. Other profile-local settings are retained.

**Google account support requires CLI 1.5.7 or later.** Its SSH-session detector selects file-only token load/save/refresh/remove operations instead of the shared OS keyring. Kameo supplies a nonempty `SSH_CONNECTION` in the account child environment, preserving a real existing value when present. The file is `<profile>/antigravity-cli/antigravity-oauth-token`. No parent environment is changed, but tools started by the CLI inherit the SSH indicator. This can affect tools that detect remote sessions.

Sign-in starts the normal interactive CLI. The user follows its browser URL and pastes the returned authorization code into its terminal. Antigravity performs the OAuth exchange and writes the renewable credential document itself; Kameo never handles the code. Imports require nested `token.access_token` and `token.refresh_token` strings with `auth_method` set to `consumer` or `gcp`, while retaining the rest of the document. `import-current` checks `~/.gemini/antigravity-cli/antigravity-oauth-token`; it does not access the shared keyring. Legacy `oauth_creds.json` is not an Antigravity token file.

Before each account session, a bounded five-second child `--version` probe must report a version of at least `1.5.7` (`AntigravityCompatibility.MinimumVersion`). The first `MAJOR.MINOR[.PATCH]` number in the output is used, so prefixes and build suffixes are ignored, and there is no upper bound. It uses the same isolated environment and directory; failures stop the launch before an account session starts. `AGY_CLI_DISABLE_AUTO_UPDATE=true` disables the CLI's automatic updater during managed account sessions. Directory/provider overrides, flag files, remote-control/remote-agent flags, and updater commands are rejected. Remote/background services are outside this integration. The version check is a compatibility gate, not executable signature verification. Users should point profiles at the official `agy` binary. CLI updates do not block account launches. If a future release changes its token storage, isolation could be affected until Kameo is updated.

Shared profile leases span the version probe and child process, so the same profile can run concurrently while edits, deletion, and sign-in remain exclusive. Different profiles can also run concurrently. Tokens are saved directly by Antigravity, including refreshes, and are never restored from a stale snapshot. Kameo checks for links and enforces owner-only Unix token permissions before and after a session. Profile deletion removes only that profile's files and does not revoke the Google grant.

The [official installation guide](https://antigravity.google/docs/install?tab=cli) and [CLI reference](https://antigravity.google/docs/cli/reference) describe the product and sign-in flow. The directory flag and SSH-selected token store are internal implementation details, not a stable public contract. The official SHA-512-verified 1.5.7 binaries for macOS arm64, Linux amd64, and Windows amd64 were inspected for the same file-storage branch and path. A macOS runtime probe launched the real CLI through Kameo using two synthetic accounts, concurrent refreshes, and relaunches against a loopback-only mock OAuth server, with external network, actual home-directory reads, and keyring access denied. No real Google login or billable request was made. Fresh browser sign-in and actual Windows/Linux Antigravity execution still require platform acceptance; automated tests validate Kameo's contracts using a synthetic child executable.

Enum value 2 preserves existing Gemini metadata, keys, selections, and native profiles. Existing native profiles can sign in again to create the new token file; old `oauth_creds.json` files remain untouched. CLI names `gemini` and `agy` remain compatibility aliases. No database migration is required for account support.

### Mux

The reference is the local `~/Code/Mux` implementation: `SettingsLoader.GetConfigDirectory`, `EndpointConfig`, `docs/CONFIG.md`, and CLI dispatch. Kameo supplies `MUX_CONFIG_DIR`. Imported native profiles preserve `endpoints.json`, resolving API-key and header environment references at import time so the saved identity is independent of the importing shell. API profiles store a selected adapter, base URL, and model in that native file, with `${KAMEO_MUX_API_KEY}` resolved only in the child environment.

Mux has no standalone OAuth or `setup` CLI command. Starting its normal interactive TUI invokes the first-run wizard; setup remains available through its F1 command menu. Kameo does not submit the word `setup` as an agent prompt. Mux's current adapters determine which authentication methods are available.

Mux file profiles can instead persist a shared source path in `mux_endpoints_file`. Before each launch, under the profile lease, Kameo validates and resolves that file into the profile's local `endpoints.json`. Source changes affect future launches; no writes or deletions propagate to the shared source. This accommodates arbitrary filenames without changing Mux, which loads `endpoints.json` from its config directory. Links to managed Kameo profile files are rejected. An invalid or missing source fails the launch while preserving the previous snapshot. Clearing the link restores local setup/import behavior. Shared-file environment references resolve at launch time, while one-time imports resolve at import time.

## Plan usage

`UsageService` reports subscription windows for native Claude Code and Codex profiles. The desktop checks a harness's native logins when it opens or the harness is selected, and after sign-in, import, or edits; each login's result is reused for 15 minutes, and **Refresh usage** or **View > Refresh Usage** bypasses that cache. While the desktop runs, including hidden in the tray, a background timer rechecks every Claude Code and Codex native login every 15 minutes, whether or not its harness is on screen, so results are current when the window is shown and expired sign-ins surface early. The status line names the local time of the last check. The CLI checks on each `kameo usage`. Checks use at most four concurrent profile checks, and return display-safe reports instead of throwing. Reports contain no credential material, and vendor or child-process error text is not shown except for Codex app-server error messages, which are bounded and stripped of control characters. Results are held in memory by the desktop; nothing is written to `kameo.db`. **Launch lowest usage** chooses, with `UsageService.LeastUsed`, the available report with the lowest `PeakPercent` (the highest percentage across its windows, so the binding limit decides), keeping list order on ties. API-key profiles, Antigravity, and Mux report "not applicable".

**Claude Code.** Kameo reads the freshest saved login (the scoped macOS Keychain entry when present, otherwise `.credentials.json`) and sends `GET https://api.anthropic.com/api/oauth/usage` with `Authorization: Bearer <accessToken>` and `anthropic-beta: oauth-2025-04-20`, the request Claude Code's own `/usage` makes. The response's `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, and `seven_day_oauth_apps` objects carry `utilization` (0 to 100) and an ISO `resets_at`; named entries in `limits[]` add per-model weekly windows. Unknown keys are ignored. The plan label comes from the saved login's `subscriptionType` and `rateLimitTier`. **Renewal.** A login within 30 minutes of `expiresAt`, or rejected with a 401, is renewed by `ClaudeTokenRefresh` before reporting. Refresh tokens rotate, so renewal runs only when Kameo holds the profile's preparation lease (serializing it with launches and their Keychain synchronization) and then obtains the exclusive profile lease without waiting. Every running session holds a shared lease, so a profile in use is reported as such and left to Claude Code. Under the leases Kameo re-reads the freshest usable login (Keychain or file, by `expiresAt`); if another process already renewed it, nothing is sent. An unreadable Keychain stops renewal, since it may hold a newer refresh token. The request matches Claude Code 2.1.332: `POST https://platform.claude.com/v1/oauth/token` with JSON `grant_type=refresh_token`, `refresh_token`, `client_id` (the login's `clientId`, or Claude Code's public client ID) and `scope` (the login's `scopes`, space-separated). The response's `access_token`, `refresh_token` (kept when omitted), `expires_in`, `refresh_token_expires_in` and `scope` update `accessToken`, `refreshToken`, `expiresAt`, `refreshTokenExpiresAt` and `scopes`; other fields are preserved. Once a token is issued it is written to `.credentials.json` and then the scoped Keychain item, regardless of cancellation; if the Keychain write fails, the next launch restores the newer file. `invalid_grant` reports that the user must sign in again, other failures change nothing. A 401 is retried once, only when renewal produced a different access token. Sessions started outside Kameo with the profile directory hold no lease and are not detected. **Sign-in end and account.** Reports carry `SignInEndsUtc` from the saved login's `refreshTokenExpiresAt` and `Account` from `.claude.json`'s `oauthAccount.emailAddress`. Within five days of the end (`UsageFormat.SignInWarning`) the desktop card and `kameo usage` warn to sign in again; a profile named with an email address that is signed in to a different one is flagged. Whether renewal extends `refreshTokenExpiresAt` depends on Anthropic returning `refresh_token_expires_in`; if it does not, a sign-in is required when it passes. The endpoint is internal to Claude Code and was checked against Claude Code 2.1.331; responses are capped at 1 MiB and the request times out after 15 seconds. `--offline` makes no Claude request.

**Codex.** Live checks start the profile's Codex with the normal isolated launch environment (`CODEX_HOME`, `-c cli_auth_credentials_store="file"`) plus `app-server`, from the profile directory so project-local configuration is not loaded. Over newline-delimited JSON-RPC on stdio, Kameo sends `initialize`, the `initialized` notification, and `account/rateLimits/read` with `excludeResetCreditDetails`, ignores interleaved notifications, then closes stdin and kills the process tree. Codex owns any token refresh. The check holds a shared profile lease, so it runs alongside sessions but not during sign-in, edit, import, or deletion, and times out after 20 seconds. `rateLimitsByLimitId` buckets are shown with the `codex` bucket first; `primary` and `secondary` windows are labelled from `windowDurationMins` (300 is 5-hour, 10080 is weekly). Plan, credit balance, and reached-limit state are shown when present. The protocol was checked against the schema generated by `codex app-server generate-json-schema` in Codex 0.171.0.

When a live check fails, or with `--offline`, Kameo reads the newest `token_count` event with `rate_limits` from the ten most recently modified `sessions/**/*.jsonl` rollouts (last 2 MiB of each), shared-read so a running session is unaffected. That snapshot uses snake_case fields and is labelled with its timestamp. A window whose reset time has passed shows 0% because it has reset since the session; legacy `resets_in_seconds` is anchored to the event timestamp.

## Desktop

The compact shell uses the supplied chameleon assets, a harness sidebar, and a card per profile with its own **Launch** action, selection, editing, sign-in and import, and plan usage when checked. Every launch, from a card, the Profiles menu, Lowest usage or the tray, opens `LaunchOptionsWindow`: a folder (defaulting to the saved launch folder, optionally saved as the new default) and a permission level from `LaunchPermissions`, a per-harness catalog of levels and their harness flags whose first level adds no arguments. The chosen flags follow `--` on the `kameo run-profile` command line, so they pass `LaunchService` argument validation like any user argument. The last level per harness is a `preferences` row (`launch-permission-<command>`), saved only after the terminal opens. Launches from the manager show the dialog modal over it. Tray launches always show it as a standalone window, because on macOS an owned window brings its owner forward, and activating the standalone dialog brings only that window to the front. Only one dialog is open at a time. Sixteen palettes provide coordinated light/dark colors across custom content and Fluent control resources. Appearance selections are saved locally. UI text is English in this alpha.

The macOS application menu is registered during application initialization, before Avalonia installs its default menu. Window menus are attached to their respective windows, including editing commands in profile dialogs. A tray's `NativeMenu` is initialized before attaching the tray and is updated in place. Each harness has a submenu per profile (Launch..., Use as default), ticked for the selection; Claude Code and Codex with two or more native logins add Lowest usage..., which shares the manager window's usage cache and lowest-usage choice. Replacing an exported tray menu caused the initial macOS crash and is now covered by the native lifecycle smoke test.

## Extending harness support

Add a harness catalog entry, credential validation, import-location mapping, and isolated launch configuration. Update the database harness constraint through an explicit migration. Add synthetic contract tests for key/native modes, inheritance cleanup, argument handling, token persistence, and profile boundaries. The current implementation keeps four concrete contracts together rather than exposing speculative plugin interfaces.
